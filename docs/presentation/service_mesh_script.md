이번 파트는 서비스 메시와 운영 회복탄력성에 관한 내용입니다. 기존 Kong의 역할을 Istio로 전환한 과정과, 전환된 환경에서 기능·부하·장애 상황을 검증한 결과를 말씀드리겠습니다.

## 슬라이드 1

이번에 진행한 Kong 제거와 Istio Ingress 전환 작업을 말씀드리겠습니다.

기존 구조는 외부 진입과 라우팅은 Kong, Kubernetes 내부 트래픽 정책은 Istio가 담당했습니다. 이 때문에 외부 진입과 내부 Mesh의 운영 경로가 나뉘고 관측과 장애 실험도 별도로 연결해야 했습니다.

이번 전환은 Kong gateway의 기능이 부족해서가 아닌 이미 내부 Mesh를 Istio로 운영하고 있었기 때문에 진입 계층까지 Istio로 통합해 운영 구조를 단순화한 것입니다.

전환 후에는 인증을 Auth-service에 위임하고, 동일한 Envoy 경로에서 Telemetry와 트래픽 정책, Chaos 실험을 확인할 수 있게 했습니다. 이 구조를 바탕으로 기능 세 시나리오, 부하 세 단계, 복구와 지연 두 실험으로 검증했습니다.

먼저 Istio가 요청을 받은 뒤 인증과 구매 흐름을 어떻게 처리하는지 보겠습니다.

## 슬라이드 2

요청이 Istio Ingress에 들어오면 Auth-service의 내부 session status endpoint로 세션을 확인합니다. 인증 규칙을 Gateway에 다시 구현하지 않고 JWT와 세션 검증 책임은 Auth-service에 그대로 두었습니다.

유효한 세션이면 200과 함께 검증된 사용자 ID, 세션 ID, 토큰 ID를 반환합니다. Istio는 사용자가 보낸 값이 아니라 Auth-service가 확인한 세 헤더만 Order로 전달합니다.

인증 정보가 없거나 토큰이 잘못됐거나 세션이 폐기된 경우에는 401로 차단합니다. Auth-service 장애나 200밀리초 초과는 503으로 처리해 확인되지 않은 요청이 내부로 들어가지 않게 했습니다.

인증을 통과한 주문은 Outbox의 이벤트로 Kafka와 Payment에 전달됩니다. 결제 결과가 Order를 확정하고, 이벤트가 Kafka를 통해 Notification으로 전달됩니다.

이제 이 경로에서 정상 구매뿐 아니라 실패와 동시 경합까지 처리되는지 확인한 결과를 보겠습니다.

## 슬라이드 3

기능 검증의 기준은 API 호출 성공이 아니라 재고와 주문 상태가 정확하게 끝나는지였습니다.

정상 구매는 주문 생성부터 확정까지 약 3.1초가 걸렸고 재고는 42개에서 41개로 감소했으며 5xx는 0건이었습니다.

결제 실패에서는 카드사가 결제 승인을 거절했을 경우를 가정을 하였습니다. Payment와 Order가 실패 상태로 전이되고 예약 재고가 해제돼 실험 전후 모두 41개로 유지됐습니다. 잘못된 주문 확정도 발생하지 않았습니다.

동시 품절에서는 재고 42개에 10개씩 다섯 요청을 동시에 보냈습니다. 네 건만 201로 성공하고 한 건은 409로 거절돼 예약량은 40개, 초과 판매는 0개였습니다. 여기서 409는 시스템 장애를 뜻하지 않습니다. 남은 재고보다 많은 주문을 감지한 시스템이 마지막 요청을 거절해 초과 판매를 막았다는 의미입니다.

기능 검증 이후에는 같은 구매 흐름을 반복해 부하가 증가해도 끝까지 완료되는지 확인했습니다.

## 슬라이드 4

부하 실험은 HTTP 200 횟수가 아니라 하나의 구매 흐름이 끝까지 완료됐는지를 측정했습니다.

단계는 상품 조회, 주문 생성, 결제 승인, 주문 확정, 알림 확인까지 다섯 단계로 구성했습니다.

동일한 AWS 환경에서 각 단계를 5분 동안 실행했고, 분당 6건, 12건, 24건으로 입력량을 두 배씩 높여 30건, 60건, 120건을 만들었습니다.

완료율과 E2E p50·p95뿐 아니라 Kafka lag, Outbox pending, Pod 재시작도 함께 확인해 비동기 처리가 뒤에 쌓이지 않는 것까지 성공 조건에 포함했습니다.

이 기준으로 세 단계의 결과를 비교한 것이 다음 표입니다.

## 슬라이드 5

세 단계에서 실행한 총 210개의 구매 흐름은 모두 주문 생성과 결제 승인, 주문 확정까지 완료됐습니다.

분당 6건의 p95는 2.257초, 분당 12건은 2.253초, 분당 24건은 2.224초였습니다. 입력량을 네 배로 높였지만 전체 구매 여정의 p95는 약 2.2초대로 유지됐습니다.

실험 종료 시점의 Kafka lag와 Outbox pending은 모두 0이었고 Pod 재시작도 없었습니다. 따라서 API 응답뿐 아니라 비동기 이벤트까지 밀리지 않고 210개 구매 흐름이 완료됐다고 판단했습니다.

이 결과를 기준선으로 삼아 실제 Pod 교체와 네트워크 지연을 주입했습니다.

다음은 장애를 직접 발생시켰을 때 복구 시간과 요청 영향을 측정한 결과입니다.

## 슬라이드 6

왼쪽은 Order Pod 복구 실험입니다.

Order v1 Pod 한 개를 Eviction API로 교체했고 요청은 HTTP 201로 수락됐습니다. PDB의 `minAvailable 1`을 유지한 상태에서 새 Pod가 생성됐고, Order Pod 두 개가 모두 Ready가 되기까지 약 14.6초가 걸렸습니다.

Ready 표시만 확인하지 않고 교체 후 실제 구매를 다시 실행해 로그인부터 주문, 결제, 확정까지 성공하는 것도 확인했습니다.

오른쪽은 Chaos Mesh의 네트워크 지연 실험입니다. Ingress Pod 한 개에서 Order v1 Pod 한 개로 가는 경로에 30초 동안 500밀리초와 50밀리초 지터를 주입했습니다.

Chaos가 Run 상태가 된 뒤 46개 요청을 관측했고 모두 HTTP 200으로 응답했습니다. 이 중 19개는 400밀리초 이상이었고 p95는 561밀리초까지 상승했지만 5xx는 0건이었습니다.

이렇게 Pod 교체의 복구 시간과 실제 구매 성공, 네트워크 지연의 응답 영향을 같은 Istio 관측 경로에서 수치로 확인했습니다.

마지막으로 이번 전환과 실험에서 확인한 결과를 정리하겠습니다.

## 슬라이드 7

정리하면 이번 작업은 Gateway 제품만 교체한 것이 아니라 외부 진입, 인증 위임, 트래픽 관측과 장애 실험을 하나의 운영 경로로 통합한 작업입니다.

기능 시나리오 세 개에서 재고 불변식을 유지했고, 총 210개 구매 여정은 비동기 적체 없이 모두 완료됐습니다.

Order Pod는 약 14.6초에 Ready로 복구됐고, 네트워크 지연 상황에서도 46개 요청이 모두 응답했으며 5xx는 발생하지 않았습니다.

이제 같은 관측 기준을 사용해 장기 부하, 다중 Pod·Node 장애까지 확장할 것입니다.
